# The Zod backend

Design document.
[zod-backend-plan.md](zod-backend-plan.md) orders the work.

The Zod backend turns a resolved model into a TypeScript module of [Zod](https://zod.dev) schemas.
It is called `zod` in a target block, ships compiled into `tdl` and as `tdl-gen-zod`, and is implemented in `backend/zod`.

Each declaration becomes a schema that parses the JSON wire convention, the one [schema-backends.md](schema-backends.md) describes and the TypeScript, JSON Schema, and OpenAPI backends write, and a type inferred from it.
The output targets Zod 4.3 or later, the release that added `.exactOptional()`, and type checks under `tsc --strict`.

## Why a backend of its own

The `typescript` backend writes declarations and no runtime code, and that is its promise: a file a consumer can include with no dependency.
A Zod module is runtime code with a dependency, so it is a target of its own rather than a directive on `typescript`.
Keeping them apart also keeps `typescript`'s importer simple, since `reverse.go` reads interfaces and aliases, not calls.

The two describe one wire format, and the Zod output is written so that its inferred types are the `typescript` backend's types, apart from what [Constraints](#constraints) adds.
Without brands (the `structural` directive), the inferred type of every declaration is mutually assignable with the interface or alias `typescript` writes for it, and a test holds the two to that (see [Checking the output](#checking-the-output)).
The module does not import the `typescript` backend's output, since that would make one target block depend on another's `out`; it infers its own types.

Where the Zod backend has no reason to differ from `typescript`, it does not: names, the primitive mapping, the discriminant, externs, and file placement follow it, and the code that decides them moves to a package both read (see [Overlap with other targets](#overlap-with-other-targets)).

## How the type-system preference applies

Every other backend that validates chooses between a check a consumer must remember to run and a type that refuses a violating value, and the project prefers the type: [rust-backend.md](rust-backend.md) and [python-backend.md](python-backend.md) write no `validate` method.
In Zod the schema is the validator, so there is no separate check to forget; what the preference decides here is what the inferred type carries after the parse.

A schema that checks `quantity >= 1` and infers `number` throws the fact away at the boundary: code holding a `LineItem` cannot tell a parsed one from an object literal with `quantity: 0`.
So the backend reads the preference as three rules:

1. **State it in the type where TypeScript can.**
   A `oneOf`, a small integer range, and a small exact list length infer literal unions and tuples, exactly as `typescript`'s `narrow.go` writes them, so `z.infer` refuses a violating literal at compile time with no brand.
1. **Brand what TypeScript cannot state.**
   A constraint TypeScript has no type for (a pattern, a wide range, a string length) is checked by the schema and recorded in the output type with `.brand()`, so a `LineItemQuantity` is a number that went through the check, as a Rust or Python checked type is a value that went through its constructor.
   Zod brands only the output type: `z.input` stays plain, so parsing JSON needs no cast, which is the cost that made `typescript` write a newtype as a plain alias.
1. **Keep every check local.**
   A check lives on the schema of the value it constrains, never in a `superRefine` on a containing object, so a value is valid when each of its parts is and no check walks a model, as in the Rust and Python designs.
   A constraint uses Zod's built-in check where one means what TDL means (`.min()` on a number, `.regex()`), and a `.refine()` only where none does, since a built-in check is what `z.toJSONSchema` and other tools read.

## What it emits

One file per model, `<last segment>.zod.ts`, under the target's `out`, so `billing.zod.ts` for package `shop.billing`, or `model.zod.ts` for a model without one, as `typescript` names `model.ts`.
The `.zod.ts` suffix lets a `zod` and a `typescript` block share an `out`.

```ts
// Code generated by tdl. DO NOT EDIT.

import * as z from "zod";

/** An order, identified by its id. */
export const Order = z.object({
  id: z.uuid(),
  createdAt: instant,
  get items() {
    return z.array(LineItem);
  },
  note: z.string().exactOptional(),
  shipOn: z.iso.date().nullable(),
});
export type Order = z.infer<typeof Order>;
```

A declaration is a `const` schema and a `type` of the same name, which TypeScript keeps in separate namespaces; that is how Zod's own documentation names them, and a consumer writes `Order.parse(json)` and `(o: Order) => ...` with one import.
Declarations are written in source order.
A `const` cannot be read before it is initialized, so a field naming a declaration written later, or one reaching back to its own declaration, is a getter, which Zod reads only when it parses; every other field is a plain property.
TypeScript cannot always infer a getter in a cycle, so each getter carries its return type, written by the same walk that writes the schema: `get items(): z.ZodArray<typeof LineItem>`.

The backend writes no `package.json`; `zod` is the consumer's dependency, as Pydantic is under Python's `json("pydantic")`.

## The type mapping

| TDL | Schema | Inferred | Why |
| --- | --- | --- | --- |
| `string` | `z.string()` | `string` | |
| `int`, `int64` | `z.int()` | `number` | A safe integer: JSON's number is a double, so a larger one has already lost precision when parsed. |
| `int32` | `z.int32()` | `number` | Zod checks the 32-bit range. |
| `uint32` | `z.uint32()` | `number` | |
| `uint64` | `z.int().nonnegative()` | `number` | |
| `float32` | `z.float32()` | `number` | Finite and within single precision's range. |
| `float64` | `z.number()` | `number` | Zod 4 refuses `NaN` and infinities, which JSON cannot hold. |
| `bool` | `z.boolean()` | `boolean` | |
| `bytes` | `z.base64()` | `string` | |
| `decimal` | `z.string().regex(decimal)` | `string` | The wire convention's decimal string; `decimal` is declared once in the module. |
| `uuid` | `z.uuid()` | `string` | |
| `instant` | `instant`, declared once | `string` | RFC 3339 with an offset, as the convention writes it. |
| `date` | `z.iso.date()` | `string` | |
| `duration` | `z.iso.duration()` | `string` | |

The inferred types are `typescript`'s, column for column.
`instant` is `z.iso.datetime({ offset: true })` with a check that seconds are present, declared once in the module, since Zod's pattern lets `12:30Z` through and RFC 3339 does not.
A primitive's format is part of what the primitive is, so it is checked and not branded: a `uuid` field infers `string`, as `typescript` types it.
The checks are what a primitive means on the wire, which `typescript` cannot say and JSON Schema says with `format`.

`int`, `int64`, and `uint64` lose the values above 2^53, as they do in `typescript`, but here the loss is a refusal rather than silent rounding, since `z.int()` refuses an unsafe integer.

Collections:

| TDL | Schema | Inferred |
| --- | --- | --- |
| `List<T>`, `[T]` | `z.array(T)` | `T[]` |
| `Set<T>`, `{T}` | `z.array(T).refine(unique)` | `T[]` |
| `Map<K, V>`, `{K -> V}` with a string key | `z.record(K, V)` | `Record<K, V>` |
| `Map<K, V>` with a fieldless enum key | `z.partialRecord(K, V)` | `Partial<Record<K, V>>` |

A set is an array on the wire, so its schema is an array refusing duplicates.
Zod has no uniqueness check, so `unique` is the one helper the module declares for it, comparing elements by a canonical JSON encoding with sorted keys, since two equal objects are distinct references.
`z.partialRecord` is how Zod spells `typescript`'s `Partial<Record<E, V>>`; `z.record` with an enum key would demand every key.
A map with an integer key is `Record<number, V>` in `typescript`, and JSON's keys are strings, so phase 1 settles whether Zod 4's `z.record(z.int(), V)` reads numeric strings as keys; if it does not, the key is a string checked against the decimal-digit pattern JSON Schema writes, the inferred type is `Record<string, V>`, and the field warns that it differs from `typescript`'s.

Absence:

| TDL | Schema | Inferred |
| --- | --- | --- |
| `name: T?` | `T.exactOptional()` | `name?: T` |
| `name: T \| null` | `T.nullable()` | `name: T \| null` |
| `name: T? \| null` | `T.nullable().exactOptional()` | `name?: T \| null` |
| `[T?]` | `z.array(T.nullable())` | `(T \| null)[]` |

`exactOptional` lets the key be absent and refuses an explicit `undefined`, which JSON cannot carry, so the inferred property is `name?: T` as `typescript` writes it, rather than `.optional()`'s `name?: T | undefined`.

## Structs

Entities, values, and mixins all lower to `ir.Struct`, and each is a `z.object`.
A mixin is a schema of its own, since a consumer may name it; an including struct carries the mixin's fields directly, as lowering copied them and as `typescript` writes them, rather than spreading `Mixin.shape`, which would change the inferred type's display but not its meaning.

`z.object` accepts a property it does not declare and strips it, so a newer producer adding a field still parses, as an open JSON Schema object validates.
A `closed` directive on a struct or an enum, or on the target block for every one, writes `z.strictObject`, which refuses an undeclared property, the directive JSON Schema and OpenAPI read for `additionalProperties: false`.

A field's default is `.default(value)`, checked against the field's schema at generation time; one that fails warns and is dropped.
A default makes the field optional in `z.input` and leaves it required in `z.infer`, so a parsed value always holds it, and the inferred type still matches `typescript`, whose interface types the parsed value.
A default on a foreign type warns and is dropped, since the backend cannot check it.

## Enums

A fieldless enum is `z.enum` of its tags:

```ts
export const Status = z.enum(["Draft", "Placed", "Provisional"]);
export type Status = z.infer<typeof Status>;
```

The values are `emit.Tag`, the variants' names in the model, which is the union of string literals `typescript` writes.
A variant's doc comment and deprecation have no place in the array, as they have none in `typescript`'s union.

An enum where any variant carries fields is a discriminated union of one object per variant:

```ts
export const PaymentCard = z.object({
  kind: z.literal("Card"),
  last4: z.string(),
});
export type PaymentCard = z.infer<typeof PaymentCard>;

export const PaymentCash = z.object({
  kind: z.literal("Cash"),
});
export type PaymentCash = z.infer<typeof PaymentCash>;

export const Payment = z.discriminatedUnion("kind", [PaymentCard, PaymentCash]);
export type Payment = z.infer<typeof Payment>;
```

Variant schemas are named as `typescript` names their interfaces, the enum's name followed by the variant's, and a `name` directive on a variant renames it.
The discriminant is `emit.Discriminant`, `kind` unless a `discriminant` directive renames it, and a variant field named like it warns and skips the enum, as in `typescript`.
`z.discriminatedUnion` picks the variant from the property before parsing it, so an error names the variant's fields rather than every variant's.

## Newtypes and aliases

A newtype is a schema of its own, branded:

```ts
export const Sku = z.string().brand<"shop.billing.Sku">();
export type Sku = z.infer<typeof Sku>;
```

So a `Sku` is a `string` that came through `Sku.parse`, and a plain `string` is a compile error where a `Sku` is expected, which is what a TDL newtype means and what `typescript`'s plain alias cannot say.
The brand is the declaration's qualified name, so two packages' `Sku` stay distinct.
A newtype over a newtype brands its parent's schema again, `export const WorkEmail = Email.refine(...).brand<"shop.WorkEmail">()`, and Zod's brands stack, so a `WorkEmail` is an `Email`, checked once for what each adds.

The `structural` directive on the target block writes no brands at all, so every inferred type is `typescript`'s, for a consumer who shares values between code using both outputs and would rather not pay for the distinction.
Under `structural` the constraints [Constraints](#constraints) brands are still checked; only the type forgets them.

An alias is expanded where it is used, as in every schema backend, and declares nothing.

## Constraints

Every `where` constraint is either a type TypeScript states, or a check whose passing the brand records.

### Constraints TypeScript states

| Constraint | Schema | Inferred |
| --- | --- | --- |
| `oneOf("USD", "EUR")` on a string | `z.enum(["USD", "EUR"])` | `"USD" \| "EUR"` |
| `oneOf(1, 2, 3)` on a number | `z.literal([1, 2, 3])` | `1 \| 2 \| 3` |
| `oneOf(Draft, Placed)` on a fieldless enum | `Status.extract(["Draft", "Placed"])` | `"Draft" \| "Placed"` |
| `min` and `max` on an integer, spanning at most 16 values | `z.literal([1, 2, 3, 4])` | `1 \| 2 \| 3 \| 4` |
| `length(N)` on a list, for `N` at most 16 | `z.tuple([T, T, T])` | `[T, T, T]` |

The first four are the literal unions `typescript` writes, by the same rule: the bound of 16 and the way a field's constraints combine with its newtype's are `narrow.go`'s, which moves into `backend/internal/emit` so both read it (see [Overlap with other targets](#overlap-with-other-targets)).
The tuple is new to TypeScript output; `typescript` adopts it when the rule moves, so the two still agree.
A field holding one of these needs no brand, and a newtype holding one brands the union, since the newtype is still nominal.

### Checked and branded

Each other standard constraint is a check:

| Constraint | Number | String | List or set | Map |
| --- | --- | --- | --- | --- |
| `min(n)`, `max(n)` | `.min(n)`, `.max(n)` | warn | warn | warn |
| `length(a..b)` | warn | `.refine(codePoints(a, b))` | `.min(a)`, `.max(b)` | `.refine(size(a, b))` |
| `matches(/re/)` | warn | `.regex(/.../u)` under `patterns`, else warn | warn | warn |
| `oneOf(...)` | `z.literal([...])` | `z.enum([...])` | warn | warn |
| `unique` | warn | warn | `.refine(unique)` | warn |

A string's length counts code points, as `emit.Length` defines it in every target, and Zod's `.min()` and `.length()` on a string count UTF-16 code units, so a string of four emoji is length 8 to Zod.
`codePoints` is a helper the module declares once, counting with a `for...of` loop, and `size` counts a record's keys.
A `oneOf` beside another constraint on the same value stays a literal union, and the other constraints check it; an argument another constraint excludes warns and is left out, since it could never be held.
Here **warn** leaves the declaration emitted without the check, as in JSON Schema.

A constrained newtype brands its own schema, as above.
A constraint on a field a literal type does not state gives the field a schema of its own, named for the struct and the field and branded with both, as Rust and Python name a field's type:

```ts
export const LineItemQuantity = z.int().min(1).brand<"shop.billing.LineItem.quantity">();
export type LineItemQuantity = z.infer<typeof LineItemQuantity>;

export const LineItem = z.object({
  sku: Sku,
  quantity: LineItemQuantity,
});
```

So `const item: LineItem = { sku, quantity: 0 }` is a compile error, and `LineItemQuantity.parse(0)` throws.
A variant's field is `<Enum><Variant><Field>`, `PaymentCardLast4`, and the `newtype` directive on a field names its schema instead.
A constraint on an optional field constrains the value inside, so `note: string? where { length(..500) }` is `OrderNote.exactOptional()`.

Every check names the type, the field when there is one, and the constraint as written in its message, `LineItem.quantity: min(1)`, and Zod's issue path adds where in the input it was.

### Patterns

A `matches` check runs a pattern the model's author wrote against input an attacker may control, on an engine that backtracks (see below), so it is opt-in.
Without the `patterns` directive on the target block, each `matches` warns that it is not checked and its schema is emitted without it, so the default output never runs a regular expression the author wrote.
The module's own `decimal` and `instant` checks are fixed patterns with no nested repetition, and run either way.

Under `patterns`, `matches` is not copied as written, because JavaScript's `RegExp` differs from RE2 in ways that change what a pattern accepts:

- `\s` is Unicode whitespace in JavaScript, so it matches a no-break space, where RE2's is ASCII.
- `\p{Greek}` is a syntax error under JavaScript's `u` flag, which spells it `\p{Script=Greek}`, and without the flag `\p` is the letter `p`.
- `(?i)`, `(?s)`, and `(?m)` are not JavaScript before ES2025's modifiers, which not every engine a consumer runs supports.
- Without `u`, `.` and a class match a UTF-16 code unit, so `^.$` refuses one emoji.
- `.` refuses `\r`, U+2028, and U+2029 in JavaScript, and only `\n` in RE2.
- `(?P<name>...)` is a syntax error.

So the backend parses the pattern with `emit.Pattern` and prints the `regexp/syntax` tree in ECMAScript syntax, as the Rust, Java, .NET, and Python designs each print it for their engine.
The printed pattern is a regex literal with the `u` flag and no other, so the engine matches code points, as RE2 matches runes, and its escapes are strict:

| `regexp/syntax` | ECMAScript |
| --- | --- |
| a literal | itself, with a syntax character or `/` escaped, and a non-printable as `\u{...}` |
| a case-folded literal | the class of its folds from `unicode.SimpleFold`, so `(?i)k` matches the Kelvin sign as in RE2, with no `i` flag |
| a class | its ranges, as `regexp/syntax` resolved them, `\d` as `[0-9]` and `\p{Greek}` as Greek's ranges |
| any character but newline, any character | `[^\n]`, `[\u{0}-\u{10FFFF}]` |
| beginning and end of text | `^`, `$`, which match only at the ends without the `m` flag |
| beginning and end of line | `(?<=^\|\n)`, `(?=\n\|$)` |
| `\b`, `\B` | themselves, ASCII in JavaScript without the `i` flag, as in RE2 |
| a named capture | `(?<name>...)` |
| repetition, alternation, groups, laziness | themselves |

Printing every class as ranges costs a long pattern for a Unicode class, and buys a pattern that means what `emit.Pattern` checked with Go's Unicode tables, whatever Unicode version the consumer's engine has.
Each pattern is a module-level constant beside the schema that uses it, so it is compiled once, and `.regex()` tests it unanchored, as `matches` reads.
A pattern RE2 refuses warns at generation time and its schema is emitted without the check.

RE2 has no backreferences and no lookaround, and the printer writes lookbehind only for the line anchors, so every printed pattern is one a linear-time engine could run.
V8, SpiderMonkey, and JavaScriptCore backtrack by default, so a pattern such as `(a+)+$` takes exponential time on a hostile string, and a schema parsing untrusted JSON runs it on the parser's thread.
The pattern is the model author's, not the attacker's, so the backend refuses the shape rather than the constraint: a pattern with an unbounded repetition nested inside another, or an alternation under an unbounded repetition whose branches can match the same text, warns at generation time and its schema is emitted without the check, as a pattern RE2 refuses is.
That catches the classic exponential shapes from the `regexp/syntax` tree; it is a heuristic, and polynomial backtracking such as `a*a*a*$` remains.
Opting in to `patterns` is accepting that remainder for the patterns the model holds; [Open questions](#open-questions) weighs a linear-time engine that would remove it.

## Units

TypeScript reduces no unit, so until phase 6 a unit-typed field is its base type with a warning, as in every backend without units.

That phase brands the number or decimal string with the unit's base dimensions as `ir` interns them, so `float64<N>` and `float64<kg*m/s^2>` carry one brand and `float64<m>` another, and a consumer cannot pass metres where newtons are expected.
Arithmetic on a branded number returns a plain `number`, so the unit holds only until the first operation, as Python's nominal option does; the brand is what the wire can carry, and arithmetic is the consumer's.
A unit parameter on a generic declaration waits on [Generics](#generics).

## Generics

`typescript` writes no generics yet, and the Zod backend shares its type mapping, so generics are a later phase for both.

A parameterized declaration is a function from its parameters' schemas to a schema, and a type over its parameters' types, written by the TypeScript mapping:

```ts
export const Page = <T extends z.ZodType>(item: T) =>
  z.object({ items: z.array(item), next: z.string().exactOptional() });
export type Page<T> = { items: T[]; next?: string };
```

The type is written rather than inferred, since `z.infer` of a generic function's result needs an instantiation expression at every use, and a test holds `z.infer<ReturnType<typeof Page<typeof Order>>>` equal to `Page<Order>`.
A `requires` constraint bounds the schema parameter's output, `T extends z.ZodType<Auditable>`, with `Auditable` the class's type under [Classes](#classes).
A parameter of a higher kind has no TypeScript spelling, warns, and skips its declaration, and `emit.Cascade` skips what names it.

## Classes

A class is a structural type, as in Python: `export type Auditable = { createdAt: string; updatedAt: string }`, the fields it declares, intersected with the classes it requires.
A satisfying struct writes nothing, since TypeScript is structural and the compiler already refused a satisfying type that lacks a field.
A class has no schema, since nothing is parsed as a class; it exists to bound a generic parameter.
The plan is `emit.PlanInterfaces`, which Go, C#, Rust, and Python read, and the rows of Python's table under [python-backend.md](python-backend.md#classes) apply as written: an empty class narrows nothing and warns, a conditional instance holds for every argument and warns, a class of arrow kind is skipped.

## Codecs

Without a directive, every schema parses JSON values into JSON values: an `instant` is a string, a set an array, a map a record, as the inferred types match `typescript`'s.

`codec` on the target block makes each schema a Zod codec that decodes wire values into richer ones and encodes them back, so `Order.decode(json)` holds a `Date` and `Order.encode(order)` is ready for `JSON.stringify`:

| TDL | Decoded | Through |
| --- | --- | --- |
| `instant` | `Date` | `z.codec(instant, z.date(), ...)`, refusing more than three fractional digits on decode |
| `bytes` | `Uint8Array` | `z.codec(z.base64(), z.instanceof(Uint8Array), ...)` |
| `Set<T>` | `Set<T>` | `z.codec(z.array(T), z.set(T), ...)`, refusing a duplicate on decode |
| `Map<K, V>` | `Map<K, V>` | `z.codec(z.record(K, V), z.map(K, V), ...)` |

`int64` stays a number, since `JSON.parse` has already rounded it, and `decimal`, `date`, and `duration` stay strings, since JavaScript has no standard type for them until `Temporal` ships everywhere.
A `Date` holds whole milliseconds, so the `instant` codec refuses a finer fraction rather than decoding `.123456Z` into a value that encodes back as `.123Z`.
A brand applies to the decoded value.
Under `codec` the inferred types are no longer `typescript`'s, and the test holding the two together runs `z.input` against `typescript`'s types instead.

## Foreign types and externs

`foreign("module", "Name")` maps a declaration to a schema another module exports, imported as `import { Name } from "module"`; Zod's convention of one name for the schema and its type means the type comes with it.
A `where` constraint on a foreign declaration warns, since the backend does not know what the schema holds.

An extern resolves as in `typescript`: through `foreign`, or else through its dependency's `zod` target block, imported from that block's file by a path relative to this one, from both blocks' `out` directives, ending in `.zod.js` as Node's resolution requires.
`typescript`'s `extern.go` already computes that path, and the Zod backend reads it from the shared package.
An extern with neither mapping warns and is skipped, and so is each declaration naming it.

## Directives

The backend declares all of these in its handshake.

| Directive | On | Does |
| --- | --- | --- |
| `name("Account")` | a declaration, field, or variant | the TypeScript name, as in `typescript` |
| `discriminant("type")` | an enum or the target block | the property a fielded enum switches on |
| `foreign("module", "Name")` | a declaration or an extern | the module and the schema it exports |
| `closed` | a struct, an enum, or the target block | `z.strictObject`, refusing undeclared properties |
| `structural` | the target block | writes no brands, so every inferred type is `typescript`'s |
| `newtype("Quantity")` | a constrained field | the name of the field's schema |
| `codec` | the target block | decodes into the richer types under [Codecs](#codecs) |
| `patterns` | the target block | checks `matches` constraints, which otherwise warn (see [Patterns](#patterns)) |

A directive the backend does not declare is a compiler warning and is passed through anyway.
`key` is not read: `typescript` and JSON Schema write no identity, and nothing in a schema would use one.

## Names

Every name is the one `typescript` writes: a declaration and a variant schema in Pascal case, a property as the model spells it and quoted when it is not an identifier.
A name TypeScript reserves, a name two declarations take, and a name the module declares for itself (`z`, `unique`, `codePoints`, `size`, `decimal`, `instant`) warn and skip the declaration, which `name` resolves.
A field's schema, `LineItemQuantity`, is held to the same rule as a declaration.

## Deprecation and documentation

A doc comment becomes a JSDoc comment on the schema and its type, and on a property in the object literal, which an editor's hover shows on the inferred type's property too.
A deprecation is `@deprecated`, as `typescript` writes it.
`.describe()` is not written, since a JSDoc comment is what the editor reads and `z.toJSONSchema` is not this backend's job.

## Diagnostics

These warn with the node's position, and the declaration reaching one is skipped: an extern with no mapping, a higher-kinded parameter, a variant field named like the discriminant, and a name collision.
`emit.Cascade` then skips every declaration naming a skipped one.

These warn and the declaration is still emitted: a unit until phase 6, a `matches` without `patterns`, a `matches` pattern RE2 refuses or whose shape backtracks exponentially, a constraint on a type its row warns for, a `where` constraint the backend gives no meaning to, a `oneOf` argument another constraint excludes, a default that fails its field's check, a default or constraint on a foreign type, and a class the plan refuses.

## Checking the output

The tests run `tsc --noEmit --strict --exactOptionalPropertyTypes` over every response when `tsc` and the `zod` package are found, as the `typescript` tests run `tsc`, and `checks.gen-zod` always does, with `zod` from a fixed-output npm fetch.

Three kinds of test hold the design's claims:

- A parse test runs each response under `node` against JSON that the smoke model's other backends accept or refuse, so a constraint is shown to refuse a value by refusing it.
- A compile-must-fail test is a snippet beside the response that `tsc` must reject, such as a `LineItem` literal with `quantity: 0` or a plain `string` where a `Sku` is expected, since the brand's claim is that the checker refuses it.
- An agreement test, under `structural`, generates the smoke model with both `zod` and `typescript` and type checks a file asserting that each inferred type and its interface are assignable to each other.

A fourth runs the printed patterns: for each case in a shared table of patterns and inputs, `node` and Go's `regexp` must agree on every input, so the ECMAScript printer is held to RE2's meaning rather than to its own reading of it.

## Reverse

An importer is not planned.
A Zod module is code, and reading it means evaluating it, which `z.toJSONSchema` already does; the route back is that output through a JSON Schema importer, once [reverse-plan.md](reverse-plan.md) orders one.

| Piece | Shared with | Where |
| --- | --- | --- |
| The primitive mapping, names, reserved words, property quoting | TypeScript | moves from `backend/typescript` into `backend/internal/ts` |
| An extern's import path from both blocks' `out` | TypeScript | `backend/typescript/extern.go`, moving the same way |
| A small range or `oneOf` as a literal union | TypeScript, Python | `narrow.go`, moving into `backend/internal/emit` |
| The wire convention, `kind` and tags | TypeScript, JSON Schema, OpenAPI, Go, Python | `emit.Discriminant`, `emit.Tag` |
| `closed` | JSON Schema, OpenAPI | design only |
| `length` counted in code points | Every backend that validates | `emit.Length` |
| The RE2 check | Every backend that validates `matches` | `emit.Pattern` |
| A pattern printed from `regexp/syntax` | Rust, Java, .NET, Python | a walk in `backend/internal/emit` with a table per engine |
| The class plan | Go, C#, Rust, Python | `emit.PlanInterfaces` |

[java-backend.md](java-backend.md#overlap-with-other-targets) puts the pattern walk in `backend/internal/emit` beside `Pattern`, with a small table per engine, written by whichever backend is built first.
None is built yet, so if Zod is first it writes the walk, and the ECMAScript table is the one this design describes.
Like Python's, it prints every Unicode class as ranges.

JSON Schema and OpenAPI copy a pattern as written today, and JSON Schema reads it as ECMA-262, so they inherit every difference listed under [Patterns](#patterns): `\s` widens and `(?i)` is refused.
Once the ECMAScript table exists, those backends can print through it too, without the slashes, though a JSON Schema validator chooses its own flags, and one without `u` reads `\u{...}` differently, so that printing needs a variant without the escape.
That change is the JSON Schema backend's to make, and the plan lists it as a follow-up rather than a phase.

## Open questions

- **Linear-time patterns.** V8's experimental linear engine runs a pattern with the `l` flag behind `--enable-experimental-regexp-engine`, and every printed pattern qualifies; an `engine("linear")` directive could add the flag for a consumer who controls Node's flags. It is not standard JavaScript, so it could only ever be a stronger form of `patterns`, never the default.
- **Zod Mini.** `zod/mini` writes the same schemas as functions, `z.optional(z.string())`, which a bundler can shake. A `flavor("mini")` directive would print the other spelling from the same plan.
- **Readonly output.** `.readonly()` freezes a parsed object and makes its type `Readonly`, as Python's dataclasses are frozen; it would also make the inferred types differ from `typescript`'s.
- **Other validators.** Valibot and ArkType parse the same convention with different spellings. The plan here, which check each constraint becomes and what the output type carries, is not Zod's, and a second validator would show where to split it from the printing.
- **Brands at the default.** Branding every newtype and constrained field is the type-system choice, and `structural` turns it off; if most consumers turn it off, the default should flip.
