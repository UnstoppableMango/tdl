# The CML backend

Design document.

The CML backend turns a resolved model into [Context Mapper](https://contextmapper.org) Language, so a model is read, reviewed, and drawn as domain-driven design: bounded contexts, aggregates, entities, value objects, and the relationships between contexts.
It is called `cml` in a target block, ships compiled into `tdl` and as `tdl-gen-cml`, and is implemented in `backend/contextmapper` on the shared pieces [schema-backends.md](schema-backends.md) describes.

It is a view of the model, as [likec4-backend.md](likec4-backend.md) is, not a code generator.
Context Mapper's own generators (context map diagrams, PlantUML, MDSL, Service Cutter, Freemarker) take it from there.
It imports nothing; [contextmapper-spike.md](contextmapper-spike.md) says why, and records the probes this design rests on.

## Output

Each response writes one file, `<package id>.cml`, holding one `BoundedContext`, and a `ContextMap` when the model imports another package (see [Context map](#context-map)).
The package id is the package's segments joined with `_`, so `shop.billing` is `shop_billing.cml`; a model with no package is `model.cml`.
The target's `out` is the directory the file is written to.

The file starts with `// Code generated by tdl. DO NOT EDIT.`, then the package's doc comment as `//` lines.

## Bounded context

The bounded context is named by the package id, or by `context("Name")` on the target block.
A name that is not a CML identifier warns with `lossy.name` and the package id is used.

The target block sets the context's properties, each written as CML spells it:

| Directive | Writes |
| --- | --- |
| `context("Name")` | the context's name |
| `type("FEATURE")` | `type = FEATURE`, one of `FEATURE`, `APPLICATION`, `SYSTEM`, `TEAM` |
| `vision("...")` | `domainVisionStatement = "..."` |
| `responsibilities("...", ...)` | `responsibilities = "...", ...` |
| `technology("...")` | `implementationTechnology = "..."` |

With no `vision`, the package's doc comment is the vision statement, joined into one line, and is not repeated as a comment.

## Declarations

| TDL | CML |
| --- | --- |
| an entity, `type X: Entity` | `Entity`, with `aggregateRoot` when it roots its aggregate |
| a value | `ValueObject` |
| a value tagged `event` | `DomainEvent` |
| a value tagged `command` | `CommandEvent` |
| a mixin | nothing: its fields are copied into each includer, as lowering already does |
| a newtype | `BasicType X { <base> value }`, the newtype's constraints on `value` |
| an alias | nothing: expanded where used |
| a fieldless enum | `enum` |
| a fielded enum | `abstract ValueObject X`, and `ValueObject XVariant extends @X` per variant |
| a class | nothing, with `lossy.class` |
| a primitive or a unit | nothing |

A fielded enum's variant is named the enum's name and the variant's, `PaymentCard`, since CML has one namespace for domain objects; `name` on the variant renames it.
CML's `Trait` is the nearest thing to a class, but 6.12 refuses a trait inside an aggregate and does not parse `with`, so a class has no spelling.

A doc comment and a deprecation are the doc string CML writes before an object, an attribute, or an enum value.

## Fields

A field typed by a primitive is an attribute, `String sku`; one naming a declaration is a reference, `- @Money total`.
A fieldless enum is a reference too, `- @Status status`, which is what the validator asks for.

| TDL type | CML |
| --- | --- |
| `string` | `String` |
| `int`, `int64`, `uint32` | `Long` |
| `int32` | `Integer` |
| `uint64` | `BigInteger` |
| `float32`, `float64` | `Float`, `Double` |
| `bool` | `Boolean` |
| `bytes` | `Blob` |
| `decimal` | `BigDecimal` |
| `date`, `instant` | `Date`, `Timestamp` |
| `uuid`, `duration` | `UUID`, `Duration`, which CML takes as Java identifiers |
| `[T]`, `{T}` | `List<T>`, `Set<T>` |
| `T?`, `T \| null` | `nullable` |

Any other primitive is `String`, with `lossy.primitive`.
A map, and a collection or optional nested in another, has no attribute form: the field is dropped with `lossy.collection`.
A type parameter, a type applied to arguments, and a unit are refused by `Resolve`, and the declaration is skipped, as in every backend.

`key(...)` on an entity marks each field it names `key`.

### Constraints

| Constraint | CML |
| --- | --- |
| `min(n)`, `max(n)` | `min = "n"`, `max = "n"` |
| `length(1..n)` | `notEmpty length = "n"`, or `size = "n"` on a collection |
| `length(..n)` | `length = "n"`, or `size = "n"` |
| `matches(/re/)` | `pattern = "re"`, the source as written |

CML's `length` and `size` take one number, so a lower bound other than 1 is lost with `lossy.constraint`.
`oneOf` and `unique` have no option (CML's `unique` is a unique column, not distinct elements), and a default has no syntax; each warns with `lossy.constraint` or `lossy.default`.
The pattern is RE2 as the source wrote it, which Java's regular expressions read alike for the common cases; CML never runs it.

## Aggregates

CML holds every domain object in an aggregate, and an aggregate has at most one `aggregateRoot`.
Lowering already says which types have identity and which fields compose, so the backend infers aggregates with no new syntax:

1. An entity that no other entity owns through an `owned` field roots an aggregate named after it.
1. An owned entity joins its owner's aggregate. A second owner warns with `lossy.owned`, and the first, in declaration order, wins.
1. A cycle of owners has no unowned entity, so its member declared first is the root, from whichever member the walk starts.
1. Any other object joins the one aggregate whose entities reach it through fields, without passing through another entity.
1. An object no aggregate reaches joins the one aggregate whose entities it names, so `OrderPlaced { order: Order }` lands beside `Order`.
1. Everything else goes in `Aggregate Shared`, which has no root.

Within an aggregate the root is written first and the rest keep declaration order; aggregates are ordered by their roots, and `Shared` is last.

`aggregate("Name")` on a declaration places it in that aggregate, overriding the rules, and an entity placed in an aggregate another entity roots is not written `aggregateRoot`.
An aggregate named only by `aggregate` directives has no root.
A declaration named `Shared` takes the name from the fallback aggregate, which is then `SharedObjects`.

## Context map

A model that imports another package refers to it by its CML file, and declares a map relating the two contexts:

```cml
import "./shop_catalog.cml"

ContextMap {
  contains shop_billing, shop_catalog
  shop_catalog [U]->[D] shop_billing
}
```

A reference into the dependency is written `- @Product product`, which validates only when the map relates the two contexts.
The import's path is relative from this file to the dependency's, which both blocks' `out` directives place, as `backend/typescript/extern.go` computes for TypeScript.
A dependency whose `ir.Import` carries no `cml` block directive is not generated beside this model: a field naming it is dropped with `lossy.unsupported`, and nothing is imported.
The dependency's `context` directive, which reaches the import, names its context.

Each file's map holds its own context and its direct dependencies, so every file validates alone and a chain of files validates.
A map of every context at once is written by hand in its own file, importing each generated one.

The relationship is upstream-downstream with no roles unless the target block says otherwise:

| Directive | Writes |
| --- | --- |
| `upstream("shop.catalog", "OHS,PL", "ACL")` | `shop_catalog [U,OHS,PL]->[D,ACL] shop_billing`: the dependency's roles, then this context's |
| `supplier("shop.catalog", "OHS", "ACL")` | `shop_catalog [S,OHS]->[C,ACL] shop_billing` |
| `partner("shop.catalog")` | `shop_billing [P]<->[P] shop_catalog` |
| `kernel("shop.catalog")` | `shop_billing [SK]<->[SK] shop_catalog` |

The first argument is the package as the import declares it.
An upstream role is `OHS` or `PL` and a downstream role `ACL` or `CF`; any other is an error the directive check reports.
Naming a package the model does not import is an error.
`exposed("Order", ...)` on the same entry is not planned; see [Open questions](#open-questions).

## Services

A type tagged `service` is a CML `Service` in the aggregate its operations touch, by the aggregate rules above, or a domain service on the bounded context when it touches several.
Each field typed by a primitive tagged `rpc` is an operation, `@GetWidgetResponse getWidget(@GetWidgetRequest request);`, using the tags the protobuf backend reads, as LikeC4 does.
A field that is not an rpc is dropped with `lossy.unsupported`.
The open question on which block's tags apply in [likec4-backend.md](likec4-backend.md) applies here unchanged.

## Names

A CML identifier is a letter or `_` followed by letters, digits, and `_`.
CML reserves about three hundred keywords, including common words (`email`, `type`, `description`, `key`, `length`, `a`) and single letters (`x`, `X`, `U`, `D`, `S`, `C`, `P`, `O`); a name among them is written with Xtext's `^` escape, `String ^email`.
`keywords.go` holds every identifier-shaped keyword of the 6.12 grammars, the literals of their enum rules included.
A name that is not an identifier at all warns and the declaration is skipped; `name("X")` on a declaration, field, or variant renames it.

## Checking the output

The tests assert on the generated text, and validate it when `cml-check` is on `PATH`.

`cml-check` is a small Java program that loads each file with Context Mapper's standalone API and prints every error and warning its validators report, exiting non-zero on an error.
The tests fail on either.
Context Mapper's own CLI, `cm validate`, is not enough: it reports only syntax errors, misses the validators (two roots in one aggregate, an unresolved reference, an object no map reaches), and exits 0 whatever it finds.
Its distribution carries the DSL's jars, so `cml-check` compiles with `javac` against them and needs no Maven.

`context-mapper-cli` is not in nixpkgs; `unmango/pkgs` packages it from the distribution its release publishes to Maven Central.
`nix/cml-check.nix` builds `cml-check` from `backend/contextmapper/testdata/cmlcheck` against that package's jars, and `checks.gen-cml` validates the smoke model's output with it.
CI's race run puts `cml-check` on `PATH`, as it does `tdl-gen-csharp`.

## Open questions

- **Exposed aggregates.** CML's `exposedAggregates` on a relationship says which of the upstream's aggregates the downstream uses. The backend could compute it from the externs the model names, or take it from a directive; computing it needs the dependency's aggregates, which the request does not carry.
- **One map for the landscape.** Per-file maps validate alone but draw one relationship each. A `landscape` target that writes one map of every package generated into an `out` would need the host to run the backend once over several models.
- **Context Mapper's release cadence.** 6.12.0 (August 2024) is the newest release; `master` moved to Xtext 2.42 in October 2026 without a grammar change. The keyword list and the trait finding should be checked again when 6.13 ships.
