# The LikeC4 backend

Design document.

The LikeC4 backend turns a resolved model into [LikeC4](https://likec4.dev) source, so a model renders as an architecture diagram.
It is called `likec4` in a target block, ships compiled into `tdl` and as `tdl-gen-likec4`, and is implemented in `backend/likec4` on the shared pieces [schema-backends.md](schema-backends.md) describes.

One model can be drawn several ways: every declaration, only the entities, or the services and what they touch.
The backend has one default mapping and a small set of directives that change it, and the other drawings are [profiles](profiles.md) over those directives.

## Output

Each response writes two files.

| File | Holds |
| --- | --- |
| `tdl.c4` | the `specification` block |
| `<package id>.c4` | a `model` block with one package element, and a `views` block |

The target's `out` is a LikeC4 project directory.
LikeC4 merges every `.c4` file under a project, so several packages generated into one `out` form one model, and a reference across packages resolves by its fully qualified name.
`tdl.c4` is the same bytes for every model, so each package writing it leaves one declaration of each kind.

Every file starts with `// Code generated by tdl. DO NOT EDIT.`

## Specification

| Element kind | For | Style |
| --- | --- | --- |
| `package` | a model's package | rectangle |
| `entity` | an entity | cylinder |
| `value` | a value | rectangle |
| `mixin` | a mixin | rectangle, dashed border |
| `enum` | an enum, either shape | rectangle |
| `newtype` | a newtype | rectangle |
| `class` | a class | rectangle, dashed border |
| `service` | a type tagged `service` | component |

| Relationship kind | For |
| --- | --- |
| `references` | a field naming a declaration |
| `composes` | an `owned` field naming a declaration |
| `includes` | a structure including a mixin |
| `conforms` | a declaration satisfying a class |
| `accepts` | an rpc's request |
| `returns` | an rpc's response |

## Packages

A model's package is one top-level `package` element.
Its id is the package's segments joined with `_`, so `shop.billing` is `shop_billing`, and its title is the package as written.
A model with no package is `model`.

Packages are flat rather than nested, because two models nesting under a shared `shop` element would each declare it, and LikeC4 refuses a second declaration.

## Declarations

Each of the model's own declarations is a child of the package element, so `Order` in `shop.billing` is `shop_billing.Order`.
Its id and title are its name, and its kind is the table's above.

An alias expands to what it names and has no element.
A primitive, a unit, and every prelude declaration have no element, so `Entity` appears only as the `entity` kind.

The `description` is markdown:

1. the doc comment;
1. the deprecation, with its reason;
1. one line per field, `- quantity: int where min(1)`, or per variant, `- Card { last4: string }`, with a mixin's fields as one `- include Timestamps`.

A type is written in TDL spelling, so the description reads like the source, and a constraint is listed rather than warned about, since a diagram enforces nothing.

The `technology` of a newtype is its base type, and of a generic declaration its signature, `Page<T>`.

## Relationships

Each field whose type names a declaration is one relationship from the field's owner:

```likec4
shop_billing.Order -[references]-> shop_billing.LineItem 'items' {
  technology '[LineItem]'
}
```

The title is the field's name and the technology the field's type.
The walk goes through lists, sets, maps, options, nullables, and type arguments, so `items: Page<LineItem>` relates to both `Page` and `LineItem`.
`emit.Resolve` refuses type arguments, so the backend walks types itself, as `backend/golang/types.go` does.

- An `owned` field is `composes`.
- Fields copied from a mixin, those with `included_from` set, are one `includes` relationship to the mixin rather than one per field.
- A variant's field relates from its enum, titled with the variant and field, `Card.last4`.
- A newtype whose base names a declaration relates to it with `references`.
- Each class a structure or enum conforms to is a `conforms` relationship, except the prelude's.

### Services

Services use the tags the protobuf backend reads, so one model's services draw and compile from the same entries.
A type tagged `service` is a `service` element.
Each of its fields typed by a primitive tagged `rpc` gives an `accepts` relationship to the request and a `returns` relationship to the response, both titled with the field's name.
A request or response wrapped in a primitive tagged `stream` has the technology `stream`.

A service field that is not an rpc is an ordinary field relationship, since a diagram has no reason to refuse it.

### Externs

A reference into another package relates to `<package id>.<Name>` in that package.
It is written when the dependency's `ir.Import` carries a `likec4` target block, so the dependency's elements are generated beside this model's.
Otherwise the relationship is dropped with a positioned warning, and the element is still written.

## Directives

| Directive | On | Does |
| --- | --- | --- |
| `element(kind)` | a declaration | the element's kind, one of the specification's; `none` omits the element |
| `edge(kind)` | a field | the relationship's kind; `none` omits it |
| `name("X")` | a declaration | the element's id |
| `title("X")` | a declaration | the element's title |
| `technology("X")` | a declaration | the element's technology |
| `link("url")` | a declaration, repeatable | a `link` on the element |
| `id("x")` | the target block | the package element's id |
| `views(false)` | the target block | omits the package view |
| `service`, `rpc`, `stream` | as in protobuf | see [Services](#services) |

`element` and `edge` are the directives profiles set, usually through kind selectors.

### Omitted elements

A relationship to a declaration omitted with `element(none)` is lifted: it is replaced by one relationship from the same source to each element the omitted declaration reaches, following omitted declarations transitively.
A lifted relationship keeps its kind and title, and its technology is the path it followed, `GetWidgetRequest.widget`.

Lifting is what makes a drawing with fewer elements still connected.
With requests and responses omitted, `WidgetService` accepting `GetWidgetRequest` that holds a `Widget` is drawn as:

```likec4
shop_widgets.WidgetService -[accepts]-> shop_widgets.Widget 'GetWidget' {
  technology 'GetWidgetRequest.widget'
}
```

An omitted declaration's own fields produce no relationship from it.

## Profiles

The default mapping draws every declaration, which is the domain map, so it needs no profile.
`prelude/std/likec4.tdl` ships two others in package `std.likec4`:

```tdl
package std.likec4

/// Entities, enums, and classes, with values, mixins, and newtypes lifted away.
profile entities for likec4 {
  @value   => element(none)
  @mixin   => element(none)
  @newtype => element(none)
}

/// Services and the entities they touch.
profile services for likec4 {
  @*      => element(none)
  @entity => element(entity)
}
```

`services` omits the services themselves until a block tags them:

```tdl
target likec4 for shop.widgets with std.likec4.services {
  out("docs/c4")
  WidgetService => element(service)
}
```

## Names

An id must be a letter followed by letters, digits, `_`, and `-`, and must not be a LikeC4 keyword or reserved name such as `title`, `description`, `style`, `link`, `view`, `extend`, `this`, or `it`.
A declaration whose id breaks either rule warns and is skipped, and `name` resolves it.

A relationship to a skipped declaration is dropped with a warning, and the element it starts from is kept.
Schema backends skip the referencing declaration too, since their output would not compile; a diagram missing a relationship is still a valid diagram.

Strings are single-quoted with `\'` and `\\` escaped, and a markdown description is in `'''`.

## Views

LikeC4 draws an `index` view of the whole project when the project declares none, so the backend declares none, and a hand-written `index` does not conflict.
Each model writes one view of its package:

```likec4
views {
  view shop_billing of shop_billing {
    title 'shop.billing'
    include *
  }
}
```

`views(false)` omits it, for a project whose views are all hand-written in their own `.c4` files.

## Checking the output

The tests assert on the generated text.
`checks.gen-likec4` runs `likec4 validate --no-layout` over the output generated from `testdata/gen/smoke`, once with no profile and once with each shipped profile.
The `likec4` CLI is not in nixpkgs, so the check takes it from the `unmango/pkgs` flake input.

## Open questions

- **Which block's service tags.** `service`, `rpc`, and `stream` are directives, and a backend reads only its own target's, so a `likec4` block does not see the tags a `protobuf` block sets.
  Either the backend also reads the `protobuf` block's tags, which [Services](#services) assumes, or a `likec4` block restates them.
  A profile cannot restate them, since `rpc` and `stream` tag primitives the model declares and a profile cannot name a model's declarations.
- **Omitted and renamed externs.** `ir.Import` carries only a dependency's block-scope directives, so a relationship into a dependency cannot see that the dependency omits its target with `element(none)` or renames it with `name`, and LikeC4 rejects a relationship to an element that does not exist.
  It needs declaration-level directives on an import, the unfinished half of [ir-plan.md](ir-plan.md) phase 8b, or the warning-and-drop rule extended to every extern.
  A dependency whose `likec4` block holds no block-scope directive is also invisible, since nothing of it reaches the import.
- **Package ids.** Joining segments with `_` sends `a.b_c` and `a_b.c` to the same id, and a package whose id is a LikeC4 keyword breaks the id rule.
  `id` resolves both by hand; the backend could instead detect them and warn, as it does for declarations.
