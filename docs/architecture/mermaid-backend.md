# The Mermaid backend

Design document.

The Mermaid backend turns a resolved model into a [Mermaid](https://mermaid.js.org) class diagram, which GitHub, GitLab, and most documentation sites render with nothing installed.
It is called `mermaid` in a target block and is written in TypeScript on the JS/TS plugin SDK (`js/tdl-plugin`), in `js/tdl-gen-mermaid`.
It is not compiled into `tdl`: `tdl gen` runs `tdl-gen-mermaid` from `PATH`, as it runs `tdl-gen-csharp`.
[#1482](https://github.com/UnstoppableMango/tdl/issues/1482) is its spec; phase 1 (#1484) and the single executable (#1487) are built, and relationships and externs (#1485) and the `direction`, `hide`, and `link` directives (#1486) follow.
It is output only: nothing reads a class diagram back.

## Output

Each response writes one file, named for the package's id: its segments joined with `_`, so `shop.billing` is `shop_billing`, or `model` for a model with no package.

| `format` | File | Holds |
| --- | --- | --- |
| `"mermaid"`, the default | `<package id>.mmd` | the diagram |
| `"markdown"` | `<package id>.md` | the diagram in one fenced `mermaid` block |

The diagram starts with `%% Code generated by tdl. DO NOT EDIT.` and `classDiagram`, then the classes in declaration order, then the edges.
Mermaid refuses a diagram with no statement, so a model with nothing to draw holds one `note` saying so.

## Declarations

Each of the model's own declarations is one class, its id the declaration's name.

| TDL | Class |
| --- | --- |
| entity, value | `class Order`, one member per field |
| mixin | `<<mixin>>`, one member per field |
| fieldless enum | `<<enumeration>>`, one member per variant |
| fielded enum | `<<union>>`, plus one class per variant (`class Payment_Card["Card"]`), each joined to it by `Payment <\|-- Payment_Card` |
| newtype | `<<newtype>>`, one member: its base |
| class | `<<interface>>`, one member per field |
| a structure tagged `service` | `<<service>>`, each rpc a method |
| alias, primitive, unit | no class; an alias is expanded where it is used |

The prelude's declarations are not drawn.
Variant classes are prefixed with their enum because Mermaid's class ids share one namespace, and labelled with the variant's name as written.
A declaration's type parameters go on its class, `class Page~T~`.

A field is a member, `+List~LineItem~ items`: its type in Mermaid's generic spelling, then its name.
A structure including a mixin lists the mixin's fields among its own until phase 2 draws the inheritance edge.

A service is a structure tagged `service` whose fields apply a primitive tagged `rpc` to a request and a response, as in the `protobuf` backend.
Each such field is a method, `+getWidget(GetWidgetRequest) Widget`, and an argument wrapped in a primitive tagged `stream` is written `stream Widget`.
A field that is no rpc stays an attribute.

## Types

| TDL | Member type |
| --- | --- |
| a primitive or a type parameter | its name |
| `[T]`, `{T}`, `{K -> V}` | `List~T~`, `Set~T~`, `Map~K,V~` |
| `T?` | `Option~T~` |
| `T \| null` | `T \| null`, as text |
| a declaration | its name, with its arguments: `Page~LineItem~` |
| an extern | its name |
| a unit argument | as written: `decimal~kg*m/s^2~` |

Constraints, defaults, doc comments, and deprecation are left out without a warning: a diagram enforces nothing, and leaving them out keeps the picture small.

## Directives

| Directive | On | Does |
| --- | --- | --- |
| `format("markdown")` | the target block | writes the `.md` file in place of the `.mmd` |
| `service` | a structure | draws it as a service |
| `rpc` | a primitive of two type arguments | makes a service field applying it an rpc |
| `stream` | a primitive of one type argument | marks an rpc argument streamed |

## Distribution

`tdl-gen-mermaid` ships as a Bun single executable, so it needs no JS runtime: `bun build --compile` bundles the compiled plugin and its dependencies into a copy of Bun (`nix/mermaid.nix`).
`nix/cmd.nix` links the one written into nixpkgs' own `bun` beside the Go binaries, so `pkgs.tdl` puts it on `PATH`.
For the release tarballs and the `@unmango/tdl-<os>-<cpu>` npm packages, it is cross-compiled from one platform for linux and darwin, amd64 and arm64, with `--compile-executable-path` naming each platform's official Bun release, fetched by hash, so the sandbox needs no network.
Those are the official Bun binaries, so the linux ones need glibc, while `tdl` beside them is static.
The npm shim puts its platform package's binaries first on `PATH`, so `tdl` run through it finds `tdl-gen-mermaid`.
Node's single executable applications are not used.

## Testing

The backend's tests cannot lower TDL, so `internal/gen/plugins_test.go` records the requests tdl sends it: one beside each `testdata/mermaid/cases/*/*.tdl`, and one per conformance case and the smoke model in `testdata/mermaid/corpus/<case>/`.
`go test ./internal/gen -record` rewrites them, and with `tdl-gen-mermaid` on `PATH` also the files each generates, in `want/`; without `-record` it compares with them.
The TypeScript tests answer every recorded request, compare the files with `want/` (`TDL_RECORD=1` rewrites a case's), and run `mermaid.parse` over every diagram.
Mermaid needs a DOM, so they install a `jsdom` window as a global; `mermaid` and `jsdom` are dev dependencies only.
They run under `node --test` and `bun test`, in `checks.js-sdk-node` and `checks.js-sdk-bun`.
`checks.tdl-gen-mermaid` runs the executable `pkgs.tdl` ships and this system's portable one through `tdl gen` over the smoke model, and `checks.npm-tdl` the npm platform package's.
