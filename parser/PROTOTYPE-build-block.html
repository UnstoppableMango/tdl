Prototype, throwaway

TDL build blocks

What would it look like to build types with C-family code inside a designated build { } block? Statements (var, for, if, functions, method calls) construct declarations, and the block expands into plain TDL before lowering, so the IR and every backend stay as they are. Edit the source on the left; the right shows the TDL it expands to and where each declaration and field was built.

Assumption this prototype makes: expansion runs on syntax, before sema, like a macro. So t.fields sees only the fields the build block itself added, not a mixin's or a class's. The open questions at the bottom say what changes if it ran over the lowered model instead. Every scenario step that expands cleanly, and every "TDL today" file, passes tdl check.

Open questions this raises

    
    
      
  1. When does it run? On syntax (this prototype) it is a macro: fast and simple, but blind to the prelude, imports, mixin fields, and inherited class fields. Over the lowered model it becomes reflection: t.fields could see everything, but sema must lower twice and a build block could depend on its own output.
    2. 
      
  2. Termination. Here there is no while, loops only walk finite lists, and recursion stops at 16 calls deep. Is a cap acceptable in a spec, or should functions simply not recurse?
    3. 
      
  3. Order. Declarative TDL is order-free. copy() is a snapshot, so a field added after the copy is missing from it (see Derived types, step 2). That is the first place TDL source order would carry meaning.
    4. 
      
  4. Tooling. tdl fmt needs a second printer for the block's own syntax; go to definition on AcmeOrder has to land on new Type(t + "Order"); hover would show the expanded declaration. The "How it was built" tab is the provenance the language server would need.
    5. 
      
  5. Round trip. tdl import and internal/unlower print plain declarations, so a build block never comes back. That is fine if the block is authoring sugar only.
    6. 
      
  6. Overlap. Shared fields already have mixins, classes, and generics. The cases nothing covers today are derived types (create and patch shapes, like TypeScript's Omit and Partial) and generating one declaration per name. A smaller declarative feature such as type CreateOrder = Order without { id placedAt } might cover the first without any control flow.
    7. 
      
  7. The spec's promise. docs/spec.md says TDL has no expressions, control flow, or runtime. A build block adds expressions and control flow at compile time only; it is worth deciding whether that promise is about the model or the source.
    8. 
    

    

      Build block reference (what this prototype understands)

build { ... }                      a top-level block; anything outside it is plain TDL, passed through
var x = expr;   Type x = expr;      a variable (the type before the name is ignored)
for (var x : list) stmt             loop over a finite list: ["A", "B"], t.fields, e.variants
if (cond) stmt else stmt            cond must be true or false
void name(Type a, string b) { }     a function; return expr; returns a value
== != && || ! +                     + joins strings

new Type("Order")  new Enum("Status")  new Mixin("Timestamps")  new Class("Auditable")
new Newtype("Email", string)
