Prototype, throwaway

Two directions for build blocks

The same four modelling problems written two ways, with the plain TDL both would lower to. Nothing here runs; it exists to compare how each reads and what each costs to build.

Settled: a build block runs after lowering, so it sees every declaration, including the fields a mixin or a class brings in and declarations from imports. Whatever it produces is lowered again into ordinary declarations, so every backend and tool sees the result.

A. Zod in a build blockA build zod { } block holds real Zod 4. The zod plugin runs it against the module it already generates for the model, reads the exported schemas back as TDL, and serves the block's language server.
B. A syntax that flowsNo block and no control flow. A declaration can say from Order and list only what differs: drop, only, rename … as …, each optional, and plain fields that add or replace.

What each takes to build

A. Zod in a build block
  • Protocol. The handshake declares the block languages a plugin serves (zod). A new build request carries the lowered model and the block's text; the response returns TDL source, which the host lowers the way analysis.Imported already lowers an import that returns source.
  • Two-pass lowering. Lower the declarations, run each block, lower its output, and refuse a name that collides. Blocks either cannot see each other's output, or run in the order their references imply.
  • A runtime at check time. tdl check, and tdl gen --target go, need node and zod whenever a model holds a zod block. Nix keeps that hermetic, but it is a heavy dependency for a Go user, and arbitrary JavaScript needs a sandbox (no files, network, or clock) to keep generation deterministic.
  • Reading Zod back. A converter from Zod schemas to TDL, from Zod 4's schema definitions or z.toJSONSchema(). What TDL has and Zod lacks (Entity, owned, units) rides in .meta(); what Zod has and TDL lacks (refine, transform, plain unions) becomes loss warnings.
  • Language server. The TDL server forwards requests inside the block to the server the plugin names, over a virtual file holding the generated <package>.zod.ts followed by the block, mapping positions both ways (the pattern Vue and Volar use). It is the TypeScript content mapper run in reverse.
  • Formatting. tdl fmt leaves the block's bytes alone or hands them to the plugin.
B. A syntax that flows
  • Grammar. A from clause on type, and four body edits beside ordinary fields. That means changes to docs/spec.md, grammar.ebnf, and the derived tree-sitter and TextMate grammars.
  • Lowering. sema resolves a from once its source is fully lowered, mixins and inheritance included, in dependency order. A cycle is an error, and so is dropping or renaming a field the source does not have. Order in the file never matters, so the snapshot problem from the first prototype disappears.
  • IR. The result is a plain struct. Recording where it came from and the edits (a new derived message) is optional, but it lets backends write their own idiom: zod could print Order.omit({ id: true }) and typescript Omit<Order, "id">, and unlower could print from back.
  • Everything else comes with the grammar. Formatting, hover, go to definition, and the editors. Every derived name is written in the source, so grep finds it and go to definition needs no provenance.
  • The limit. It cannot express anything that needs computation. That is deliberate, and generics cover the family case.

My read

  1. Build B first. It covers the two cases the first prototype found worth having (derived shapes, and families of declarations through generics). It keeps the spec's promise of no control flow, and it works in every backend and tool without a runtime.
  2. A is a bigger bet about the platform, not the language. "A backend can host its own authoring language" is a strong idea, and running after lowering is exactly what makes it better than writing Zod by hand. But it turns one backend into a second front end that every consumer of the model depends on.
  3. They compose. Both produce ordinary declarations after lowering, so A can come later as a plugin capability without changing B. B's record of derivations in the IR is also what lets the zod backend write .omit() and .partial(), so B makes generated Zod read the way A's source does.
  4. Questions for B: does from carry conformance (here it does not; you write : Entity), does each optional keep constraints (here it does), and should drop accept a mixin's name to drop all its fields at once?
